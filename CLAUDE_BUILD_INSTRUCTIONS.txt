TRENDS — CLAUDE DESKTOP BUILD INSTRUCTIONS
=============================================

You are the primary implementation engineer for the Trends production e-commerce project.

You have:
1. This instruction file.
2. `TRENDS_PROJECT_CONTEXT.md`.
3. The supplied prototype `index.html` (if it is present in the project workspace).

Your job is to turn the prototype into a real production-grade Persian/RTL Iranian clothing e-commerce website.

IMPORTANT: You are working under a free-plan session limit. Work in SMALL, COMPLETE PHASES. Never attempt the entire project in one response/session.

--------------------------------------------------
A. NON-NEGOTIABLE RULES
--------------------------------------------------

1. Read `TRENDS_PROJECT_CONTEXT.md` before coding.
2. Inspect the existing repository before changing anything.
3. Inspect the prototype carefully before recreating the UI.
4. Preserve the prototype's design language.
5. Do not replace the design with a generic template.
6. Use Next.js + TypeScript + React + App Router.
7. Use Tailwind CSS plus focused CSS where useful.
8. Use PostgreSQL + Drizzle ORM unless a documented technical reason requires otherwise.
9. Use server-side validation for every mutation.
10. Treat the server/database as authoritative for all commerce values.
11. Never trust client price, stock, discounts, roles, payment state, or order totals.
12. Do not store authentication tokens in localStorage.
13. Never expose secrets to the browser.
14. Do not implement the future mobile app now.
15. Do not create microservices.
16. Do not add Redis unless the current phase has a concrete reason for it.
17. Do not fabricate live payment credentials or claim a payment integration is live when it is not.
18. Do not silently invent business requirements that materially affect money, legal policy, or payment behavior. Use sensible defaults and document assumptions.
19. Do not stop after writing code. Run checks and fix what you can.
20. At the end of EVERY phase, update or create `PROGRESS.md` in the project root.

--------------------------------------------------
E. IMPLEMENTATION RULES
--------------------------------------------------

### UI
Use reusable components.

Do not duplicate large JSX blocks.

Use semantic HTML.

Keep the visual language from the prototype:
- warm neutrals
- dark ink
- pastel accents
- rounded corners
- generous whitespace
- fashion/editorial feel

### RTL
Treat RTL as foundational, not as a final patch.

Prefer logical CSS properties:
- margin-inline
- padding-inline
- inset-inline
- text-align/start/end

Be careful with:
- icons
- carousel direction
- breadcrumbs
- price placement
- drawers
- pagination
- keyboard interactions

### Images
Use optimized image handling.

Do not load massive source images into small cards.

Require:
- alt text
- predictable aspect ratio
- lazy loading where appropriate
- appropriate priority for above-the-fold hero/LCP media
- object storage/CDN architecture when external media is introduced

### Database
Use migrations.

Add foreign keys and useful indexes.

Use transactions for multi-step commerce mutations.

Use unique constraints to enforce invariants where appropriate.

Never rely only on application code to enforce uniqueness.

### Money
Never use JavaScript floating point for monetary business logic.

Store integers.

Format only at presentation boundaries.

### Concurrency
Inventory and payment/order operations are concurrency-sensitive.

Use transactions, locking/conditional updates, unique constraints, and idempotency where appropriate.

### Errors
Do not leak stack traces, SQL, secrets, provider responses, or internal details to customers.

Log useful server-side diagnostics without logging secrets.

### Server Actions
Use Server Actions where they are a good fit for mutations/forms.

Remember that Server Actions still require:
- authentication checks
- authorization checks
- input validation
- business-rule validation

Do not treat "server action" as automatically authorized.

### Client components
Default to Server Components.

Use `"use client"` only for actual client interactivity.

Avoid putting the entire page into one Client Component.
